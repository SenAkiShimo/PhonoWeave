# PhonoWeave：用户原始标记的全批量声学候选检查 v2

这轮不再手工预选 `i / ir / i0`。`discover-user-units-batch` 直接解析声库里的 OTO 双标签表面结构，批量提取声学证据，并给已有用户标记制作差异识别与证据不足的审核队列。

## LynneQing 七音阶真实运行

- 来源：芒 G3/D4/G4/D5 与露 C4/F4/B4；同一个作者确认的 DiffSinger 声库的不同声线／音阶，并非独立的真人录制会话。
- **完整 OTO 行数 13,539**；符合自动识别双标签表面结构的候选 **7,862**；测得 **7,860** 个 70ms 声学窗口；**2** 个窗口因低能量弃判。
- 左侧 **23** 种用户表面标签，右侧 **47** 种表面上下文，涉及 **175** 个分库内源 WAV。
- 23 类标签在 **完整留出同名源 WAV 模板**时，最近原型声学分类正确率 **2,987/7,860 = 38.0%**，在留出整个音阶/声线时分别为 **38.19% / 36.22%**。这个数不是音素切分准确率，也不证明哪种应该独立录制；简单等概率 23 分类的参考水平约为 4.35%。
- 有 **5,677** 条 OTO 记录属于其他结构（单标签、前置音节等），本轮未视为可安全用同一双标签扫描器处理。
- 此前 `i/ir/i0` 的高准确率不能推广至 23 个标签：现有 70ms OTO 相对窗口以及简单 Mel-DCT 表征对所有发音上下文并不足够可靠。

## 运行方式

在 GitHub PhonoWeave 工作分支的环境中：

```bash
phonoweave discover-user-units-batch \
  --manifest examples/user_native_batch_lynneqing.example.json \
  --archive-root /你的/声库ZIP目录 \
  --output /你的/空输出路径
```

示例配置以仓库例子为准。可以用 `include_left_symbols` 限定用户符号；**不需要 IPA 或 MFA**。对其他语言，只要其声库 OTO 采用相同的两个空格分隔表面 token 结构，也可复用；其他 alias/发音文本格式需要编写输入解析适配器，声学分析部分不变。

## 输出含义

- `evidence.json`：覆盖统计、23 类留出测试与最近已有标签差异、来源门禁与解释。
- `source_index.csv`：7,860 个声学候选的原始 alias、WAV、OTO 行号、候选时间窗与原始 ZIP/WAV 哈希。
- `feature_vectors.json`：可重现分析的数值特征；**不包含私有音频**。
- `review_queue.csv`：按整 WAV 模板留出召回率排序的现有标签，帮助优先处理失败，而非要求用户逐个审核所有类型。
- `abstentions.csv`：不可安全分析的窗口。

## 严格限制

1. OTO 中空格分隔的两个表面字段未必各自都是一个语言学音素；这里只把它们视作用户内部符号与右侧上下文。
2. OTO-relative 70ms 的时间窗不是经过验证的音素核心或整音素边界。**真正独立人工验证的完整音素边界：0**。
3. 当前减去每个音阶的全体样本均值是一种利用测试音阶未标记数据的 transductive 规范化，不可称为严格零样本泛化。
4. 相同源 WAV 名称的多个 DiffSinger 音阶属于强相关样本；按文件名留出降低泄漏风险，但不等于不同真人录音批次。
5. `label_aggregated_clustering_audit` 先利用已知用户标签取均值，再聚类；它不是无监督发现新音素，不允许以其 k 最佳值创造新别名。
6. 跨源 WAV 的声学标签识别率不等于拼接合成质量；本轮不自动拆分、合并或更改任何用户 alias、OTO 或 WAV。

**结论：实现了可扩展的完整一批用户标签的发现入口和可追踪的失败排序；尚未获得足够证据的自动音素拆分器。下一步应改进从完整发声中定位对比部位与上下文分离的表征，并通过分组留出提升准确率，而不是继续逐个手动做音素。**
